## 二、根因：不是「没实现」，是「白底深字」在物理上做不出来

### 2.1 诊断包里确认的事实

诊断包（`cardesk-logs-20261112-084209.zip`）里：

- 版本 `1.0.1150-system (code 4246)`，真机 QUALCOMM MSM8996 / Android 9 / **1920×968 @160dpi**；
- `nav_cover_backdrop_enabled=true`、`daynight_applied_night_ui=false`（**日间**）、`last_page=1`（第 2 页）；
- 日志明确显示**开关是有生效的**：

```
08:41:58.547  enabled=false
08:41:59.423  enabled=true      CarDesk/NavUI: [EVT] 导航页音乐卡封面背景切换
```

→ 所以问题不在「状态没落盘 / 没刷新」，而在**画出来的东西一样**。

### 2.2 为什么画出来一样

背景层要把封面压到「压在上面的小字还能读清」的程度，区间由对比度反推（`CoverBackdrop.targetRange`）：

| | 文字 | 卡面 | 反推出来的背景亮度区间 |
|---|---|---|---|
| 夜间 | 浅（`#757E8E`，L=0.2065） | 深（`#1F232D`） | `L ≤ 0.0341`（**上限**）→ 封面被**压暗** |
| 日间 | 深（`#8B92A0`，L=0.2859） | 亮（`#FFFFFF`） | `L ≥ 0.9743`（**下限**）→ 封面被**罩成白** |

日间那条下限**只有 0.0257 宽**，整张封面被罩成**一片均匀的白** ——
和纯色卡面（也是纯白）**像素级几乎一样**。

更糟的是日间的「变亮」走 `CoverBackdrop.mixWhite`（各通道向白色插值），
**连饱和度一起冲成 0** —— 代码注释里承诺的「极淡一层色偏」其实也没了。
而且封面里**纯黑**的像素提不亮（`toneMap` 里 `lIn <= 0` 直接原样返回），
于是白底上还留着几个**黑点** —— 旧包实测截图里能直接看到。

### 2.3 物理限制是真的

白底深字要求背景 `L ≥ 0.9743`。**一张封面在纯白底上必然看不出来** ——
这跟实现得好不好无关。

**所以调映射曲线救不回来** —— 能救的只有一条：**改文字**。

（照抄 `CoverBackdrop.kt` 的 `relativeLuminance` / `targetRange` / `toneMap`）
把四条路都渲染了一遍（`tools/render_y153_day_styles.py`）：

| 画法 | 背景亮度区间 | 罩完之后比纯白暗 8 以上的像素 | 结论 |
|---|---|---|---|
| **A** 深色氛围卡 | `[0, 0.0341]` | 100%（深底） | 封面最清楚，但日间这张卡比别处深 |
| **B** 旧路：白卡 + 三档深字 | `[0.9743, 1.0]` | **0.9%** | = 旧包实测，封面等于没画 |

## 四、最终修法：日夜两套规矩

### 4.1 夜间 —— 一行不改（深底浅字，三档文字）

最弱那档 `textFaint`（`#757E8E`）→ 区间 `[0, 0.0341]` → 封面被**压暗**，清晰可见。

### 4.2 日间 —— 白底深字，**只有两档**文字

- 歌名 + 当前句歌词 = `#191C23`（`text`）
- 歌手 + 其它歌词 + 播放状态 + 时间行 = `#565D6B`（`textDim`）
- **不再用 `textFaint`**（`#8B92A0`）—— 那档会把下限顶回 0.9743

→ 区间 `[0.4340, 1.0]` → 封面留得住一层灰调影子，卡片跟日间其它卡一样白。

### 4.3 卡面：两套都尊重用户自选色，但有「读得清」的保护

```kotlin
private fun cardSurface(): Int {
    val alpha = Skin.surface ushr 24
    val rgb = Skin.surface and 0x00FFFFFF
    val l = CoverBackdrop.relativeLuminance(rgb)
    val ok = if (pal.night) {
        // 夜间：浅色字 → 底色亮度的**上限**
        l <= CoverBackdrop.maxBackgroundLuminance(cardWeakText)
    } else {
        // 日间：深色字 → 底色亮度的**下限**
        l >= CoverBackdrop.minBackgroundLuminance(cardWeakText)
    }
    return (alpha shl 24) or (if (ok) rgb else cardPal.surface and 0x00FFFFFF)
}
```

- 夜间：用户色**够暗**就沿用（默认 `#1F232D` → 零退化）；太亮换标准深色底；
- 日间：用户色**够亮**就沿用（默认纯白）；太暗换标准白底（深色字压不住）；
- alpha 段两种模式都跟用户的「卡片不透明度」走。

### 4.4 日间的强调色要加深一档

当前歌词高亮 / 进度条填充在白罩底最暗处（L=0.4340）上：

| 强调色 | L | 对比度 |
|---|---|---|
| 日间主题那个 `#0F9C8E` | 0.2584 | **1.57:1**（读不出来） |
| **加深的 `#0A6459`** | 0.0990 | **3.25:1** ✓ |

夜间仍用 `#5AD8C8`（深底上很跳）。

### 4.5 新增两个纯逻辑函数

```kotlin
/** 浅色文字压在背景上时，背景亮度的**上限**（夜间那条）。 */
fun maxBackgroundLuminance(textColor: Int): Double =
    (relativeLuminance(textColor) + 0.05) / SOLVE_CONTRAST - 0.05

/** 深色文字压在背景上时，背景亮度的**下限**（日间那条）。 */
fun minBackgroundLuminance(textColor: Int): Double =
    SOLVE_CONTRAST * (relativeLuminance(textColor) + 0.05) - 0.05
```

## 五、怎么保证不退回

### 5.1 新增测试：`NavCoverBackdropDayModeTest`（16 条）

锁住五件事：

1. 日间模式下卡面是**亮**的（跟日间其它卡一样白）；
2. 日间模式下文字是**深**的，而且只有**两档**（最弱那档不能是 `textFaint`）；
3. 亮度区间是**下限**且由 `minBackgroundLuminance` 反推；
4. 罩完之后封面**还认得出来**（没被冲成一片白）；
5. **夜间零变化**。

另外还锁了：开关真的有封面纹理、**开 / 关画面确实变了**、强调色在白罩底上够 3:1、
用户自选的亮/暗卡片色分别被沿用/换掉、卡片透明度仍然生效。

### 5.2 踩过的坑：组合卡是**构建时**建出来的

第一版测试有两条反向验证**没红**。查下来是**测试本身**的问题，不是实现的问题：

- 组合卡的文字（歌名 / 歌手 / 歌词 / 进度条）在 `NavPage.buildCombinedCard()` 里**构建期**就建好了，
  运行时切主题**不会**重建；
- 所以「先起桌面、再切主题」的写法，测到的其实是**夜间下建好的卡** ——
  主题跟着走不走的，在测试里根本看不出来。

改法两条：

1. **先写 pref、再起桌面**（`daynight_applied_night_ui`）→ 桌面冷启动就落在目标主题，
   组合卡也在那个主题下被构建；
2. `Skin` 是**单例对象**，Robolectric 同 classloader 下静态状态**跨用例泄漏** →
   每条用例跑完 `@After` 还原主题。

另外还栽过一次：**pref 的语义写反了**（`daynight_applied_night_ui = !night`），
日夜两套用例其实互换了 —— 表现是「只有夜间那条红」。这是同一天里第二次栽在
「测试自己要先站对」上，所以写进了脚本注释里。

## 九、本轮记下来的坑

1. **组合卡是构建时建出来的** —— 想测「日间」必须让桌面**在日间下冷启动**，
   否则测的是「夜间建好的卡」。
2. **`Skin` 是单例**，Robolectric 里静态状态跨用例泄漏 → 每条用例 `@After` 还原。
3. **反向脚本被打断会把源码留在坏状态** → 加 `trap restore`。
4. **断言要查「实际在用的值」，不能查常量** —— 常量对了但接线接错，查常量查不出来。
5. **判断「有没有变化」要量像素，不能靠肉眼** —— 旧包那 3.3% 的差异全是字形抗锯齿。
6. **「白底深字」的物理限制只靠改文字能绕开，改映射曲线绕不开** ——
   能绕开的唯一杠杆是「最弱那档文字有多深」。

## 十、追查「对比图上那么多黑点点」

用户看完对比图后问「为什么图片上那么多黑点点」。结论：**黑点只存在于对比图里，
真机上没有这个现象**；根因是我写的模拟脚本本身有 bug，不是 App 的 bug。

### 10.1 黑点长什么样

`emu-verify/y153/10b-blackdot-bug-vs-fixed.png` —— 左边是 bug 版，右边是修复版，
同一块 160×160 区域、同一张封面、同一套公式。

### 10.2 根因：模拟脚本把「越界回踩」写进了单像素循环

真机 Kotlin 的 `CoverBackdrop.toneMap()` 是**两趟**：

```kotlin
// 第一趟：逐像素映射（纯黑像素早退）
for (i in pixels.indices) { ... if (lIn <= 0.0) { out[i] = p; continue } ... }
// 第二趟（单独扫全图）：把越界的像素夹回区间 —— 纯黑像素也会被抬到 lo
for (i in out.indices) { ... }
```

第一版 Python 模拟脚本把「越界回踩」写在了第一趟的**单像素循环内**，
于是走 `lin <= 0` 早退分支的像素（封面里的纯黑笔画）**连回踩一起跳过了**，
留在原样。日间是近白的罩子，这些没被抬起来的暗像素看起来就是**一颗颗黑点**。

同一份数据、同一个口径（罩子层单独渲染）：

| 版本 | 掉出目标区间下限的像素 | 纯黑像素 | 罩子最暗亮度 |
|---|---|---|---|
| bug 版（回踩在循环内） | **6522（1.44%）** | 8 | 0.0003 |
| 修复版（回踩独立第二趟，对齐 Kotlin） | **0（0.000%）** | 0 | 0.9753 / 0.4342 |

### 10.3 真机侧交叉验证（emulator-5560，4248）

| 区域 | 罩子最暗亮度 | 低于下限（0.4340）的像素 |
|---|---|---|
| 歌词下方纯背景带（y 560..640） | 0.5149 | **0（0.000%）** |
| 歌手行右侧背景（y 180..230） | **0.4342**（正好压在下限上） | **0（0.000%）** |
| 整张卡片罩子区（排除缩略图） | — | 纯黑 **0（0.000%）** |
| 专辑图缩略图 | 0.0000 | 5959 —— **这是原始专辑画**，不是罩子层 |

真机上 Kotlin 的第二趟回踩把最暗的像素**精确顶到下限 0.4340**，
所以罩子上不会出现任何黑点；专辑图缩略图保留原始封面的黑三角（那是画本身，不是缺陷）。

### 10.4 结论与处置
