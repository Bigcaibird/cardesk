# 第219轮 · 视频壁纸导入加一条**不依赖系统选择器**的路（应用内视频列表）

> 第218轮修完「视频选择器」后，实车诊断包里的现场又暴露出更硬的事实：
> **车机上的系统选择器本身就不可用**。
> 本轮按用户拍板的方向做：**做应用内视频列表，系统选择器保留为备选。**

---

## 一、为什么还要再做一轮

第218轮在实车（领克 AAOS 820A）诊断包里读到的现场：

```
12:32:25.532  CarDesk/App    : onPause
12:32:25.533  CarDesk/Setting : 视频壁纸：收到选视频结果 resultCode=0 uri=null
```

两点关键：

1. **`onActivityResult` 被调用了** ⇒ 旧代码的 `startActivityForResult` **没有抛异常**，
   选择器确实被拉起过、也确实返回了 `RESULT_OK`；但返回的 Intent 里 **没有 `data`**。
2. **`onPause` 到返回只隔 1 毫秒** ⇒ 那个接手的 App 是**秒退**的，
   用户根本没机会浏览文件。

再查诊断包的 uid=1000 系统包清单（覆盖车机全部系统包 + 第三方包）：

**没有 `com.android.documentsui`** ⇒ 车机没有 AOSP 那套文档选择器。

⇒ 结论：**「靠系统选择器」这条路在车机上不可靠**，
第218轮加的三级降级链只能改善「有人接但返回得奇怪」的情况，
救不了「没人接」和「秒退不带 uri」。

## 二、我们凭什么能自己列

诊断包同一份清单里：

```
uid=1000 packages=… com.ecarx.cardesk …
```

⇒ **本包在车机上跑在 uid 1000（系统应用）**。
而且局域网传输功能早就在直接读写车机的 `Download` 目录（`Download/CarDesk`）。

⇒ 我们**可以自己扫共享存储**，列出视频文件让用户点。

## 三、改了什么

### 3.1 `core/VideoLibrary.kt`（新，纯逻辑）

| 函数 | 作用 |
|---|---|
| `libraryDir(context)` | 我们自己的目录：`Download/CarDesk` |
| `scanFiles(roots, maxDepth, limit)` | **扫目录找视频**（只碰 `java.io.File` ⇒ JVM 单测直接跑） |
| `isVideoPath` / `extensionOf` | 扩展名白名单（`.mp4/.mkv/.avi/.mov/.3gp/.m4v/.webm/.ts/.flv/.wmv/.m2ts`） |
| `sort` | 新的排前面 |
| `formatSize` | 大小文案 |

> ⚠️ **只扫 `Download/CarDesk` 这一个目录**（用户明确要求）：
> 车机共享存储里可能有几千个文件、上百个目录，递归扫一遍要几秒到几十秒 ⇒ 界面明显发顿。
> 视频进这个目录的路径是**局域网传输**（设置 → 局域网传输 → 手机扫码上传）——
> 本来就是这个 App 自己的文件通道，闭环在 App 内。
>
> ⚠️ **只在用户点「导入视频…」时才扫描**（不在启动时、不在后台扫）。

### 3.2 `ui/VideoPickerOverlay.kt`（新）

参照 [SourceMenuLayer] 的形态：全屏层 = 遮罩 + 居中面板；
面板自上而下 = 标题 / 状态行 / 可滚动列表 / 底部按钮行。
每行两行字：**文件名** + 「大小 · 日期 · 完整路径」。
底部三个按钮：**重新扫描** / **用系统选择器** / **取消**。

扫描在后台线程做，结果切回主线程刷新列表 ⇒ 打开面板不会卡。

### 3.3 `core/VideoWallpaper.kt`

- 新增 `importFromFile(context, file)`：按**文件路径**导入。
- 把拷贝逻辑抽成 `copyToWallpaper(context, input)`，
  `importFromUri` 与 `importFromFile` 共用同一套（先写 `.tmp` 再改名，避免半截文件）。

### 3.4 设置页接线

`设置 → 壁纸 → 视频壁纸` 现在是**两个**入口：

| 按钮 | 走哪条路 |
|---|---|
| **导入视频…** | **应用内视频列表**（新增，主路径） |
| 用系统选择器导入… | 第218轮的三级降级链（保留为备选） |

### 3.5 存储权限

- 清单新增 `READ_EXTERNAL_STORAGE`。
- 车机上本包是 uid 1000 系统应用 ⇒ **权限天然 granted**（实测这套系统上它是
  `SYSTEM_FIXED + GRANTED_BY_DEFAULT`，`pm grant` 都会直接拒绝，说明它就是安装即授予的）。
- 普通安装（AVD / 侧载）若权限缺失 ⇒ 走运行时申请，
  批下来后 `onRequestPermissionsResult` 自动把选择器打开。

## 四、顺带修掉的两个问题

### 4.1 导入前先删旧文件是多余的

原来 `copyToWallpaper` 里有一句 `if (out.exists()) out.delete()`。
实测 **`File.renameTo` 用的是 POSIX `rename(2)`，本身就是原子替换**（目标存在也会被换掉）：

```
renameTo=true  dst内容='new'  dst存在=true  src存在=false
```

⇒ 那句删除**纯属冗余**，而且删了有个坏处：
万一这次改名失败，旧壁纸已经被删了 ⇒ 用户的壁纸没了。
⇒ 已删掉，失败时旧壁纸还在。

### 4.2 扫描逻辑本来并不「纯」

`VideoLibrary.Item` 里原本放过 `Uri.fromFile(child).toString()`，
结果纯 JVM 单测直接 NPE（`Uri.fromFile` 在纯 JVM 下返回 null）。
⇒ 扫描只需要**路径**，把 `uri` 字段整个去掉 ⇒ 扫描层重新变成**不碰任何 Android 类**的纯逻辑。

> 这两个问题都是**单测与变异检查抓出来的**，不是读代码看出来的。

## 六、车机上的用户操作路径

1. **设置 → 局域网传输** → 启动服务 → 手机扫码 → 上传视频
   （落在车机的 `Download/CarDesk`）；
2. **设置 → 壁纸 → 视频壁纸 → 导入视频…** → 列表里点那个视频；
3. 导入完成，壁纸立即开始播放。

> 系统选择器那条路（**用系统选择器导入…**）仍然保留 ——
> 万一车机 ROM 变了、系统选择器又能用了，不用等下一版。
