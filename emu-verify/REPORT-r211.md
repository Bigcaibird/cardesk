# 第211轮 · 动态壁纸 / 静态壁纸轮播 的性能对比报告

**日期**：2026-11-19
**设备**：模拟器 `emulator-5560`（cardesk28，API 28 / Android 9 / arm64，1920×1080 @160dpi，host GPU）
**对比对象**：第207轮出的 **4285**（代码里**根本没有**这些功能）vs 第208~210轮出的 **4288**

> **本轮是纯测量，没有改代码、没有出包。**

---

## 一、结论先行

1. **「引入这些功能」本身零开销** —— 4285（没有代码）vs 4288（有代码但不启用）：CPU / 内存 / 帧率**完全一致**。
   所有开销都来自**启用**。
2. **静态壁纸轮播：CPU 开销可忽略，但内存要 +32MB。**
   每次切到一张没缓存过的壁纸，就多留一张 **1920×1080 ARGB 位图 = 8.3MB**（LRU 上限 40MB），稳态约 **90MB**。
3. **程序化动态壁纸：唯一有明显开销的功能** —— app CPU **×6.6**，宿主整机占用 **+34 个百分点（接近翻倍）**，
   帧耗时 20ms **超过 60fps 的 16.67ms 预算**（这台模拟器上 97% 的帧都超时）。
4. **视频壁纸：在这台镜像上测不出真实成本** —— 视频一帧都解不出来（`numFramesTotal(0)`），
   解码服务进程 CPU 反而是 **0.00%**，**必须实车复测**。

| 指标 | 怎么测的 |
| --- | --- |
| app CPU | 客机 `/proc/<pid>/stat` 的 utime+stime 增量 ÷ 客机整机 `/proc/stat` 增量（**占客机整机的百分比**） |

每个场景：**装对应包 → 改 prefs → 冷启动 → 静置 14 秒 → 测 60 秒窗口**。
设备上除 CarDesk 外没有别的重负载（整机 busy 稳定在 9%~12%）。

## 四、逐项解读

### 4.1 S0 vs S1 —— 「有代码」本身不要钱

| 指标 | 4285（没这功能） | 4288（全关） | 差异 |
|---|---|---|---|
| app CPU | 0.82% | 0.77% | −0.05pt（噪声内） |
| 宿主 qemu | 45.1% | 43.0% | −2.1pt（噪声内） |
| PSS | 58.1 MB | 58.1 MB | **0** |
| fps | 2.8 | 2.8 | 0 |

⇒ 轮播心跳、动态壁纸帧循环、视频壁纸这些代码**全是惰性的**：
没启用就一行代码不跑，内存一点不涨。

### 4.2 S2 静态壁纸轮播 —— CPU 几乎不涨，内存涨 32MB

**CPU**：app 0.77% → 1.06%（相对 +38%，但绝对值只 +0.29 个百分点整机）。
每秒一次的心跳只是读几个 pref，15 秒才切一次。

**但内存是实打实的**。PSS 随时间（每 10 秒采一次）：

```
t=10s  64.9 MB   切了 1 次
t=20s  73.5 MB   切了 2 次      ← 每次 +8.3MB
t=30s  73.7 MB   切了 2 次
t=40s  81.9 MB   切了 3 次
t=50s  90.3 MB   切了 4 次
t=70s  90.3 MB   切了 5 次      ← 到了上限就稳住
t=90s  90.6 MB   切了 6 次
```

对照（轮播关）：57.0 → 58.2 MB，**一路平**。

**根因**：`ui/widget/WallpaperRenderer.kt` 把每张壁纸的成品**缓存成一张全屏 Bitmap**
（1920×1080 ARGB_8888 = **8.29MB/张**），LRU 上限 `MAX_CACHE = 10` 张 / `MAX_CACHE_BYTES = 40MB`。
轮播每切一张没缓存过的壁纸，就多占 8.3MB —— **4 张就到 40MB 的天花板，之后稳态不再涨**。

⇒ **稳态代价 ≈ +32MB**（58MB → 90MB）。不会无限涨，但车机内存本来就紧张，这一项要知道。

**帧**：切换那一帧 p99 从 15~19ms 涨到 **25ms**（要重建整张壁纸的渐变 + 200 个采样点的山脊路径）。
60 秒里 7 帧卡顿（3.17%）。**间隔越短，这个抖动越频繁。**

### 4.3 S3 程序化动态壁纸 —— 唯一有实打实开销的功能

| 指标 | S1 基线 | S3 动态壁纸 | 变化 |
|---|---|---|---|
| app CPU | 0.77% | **5.09%** | **×6.6** |
| 宿主 qemu | 43.0% | **77.5%** | **+34.5pt（接近翻倍）** |
| 整机 busy | 8.92% | 15.86% | +6.9pt |
| fps | 2.8 | **53.0** | 从**按需渲染**变成**常驻 60fps 渲染** |
| 帧耗时 p50 | 7ms | **20ms** | **超过 16.67ms 的 60fps 预算** |
| 卡顿率 | 2.37% | **97.04%** | 这台模拟器上几乎每帧都超时 |
| PSS | 58.1 MB | **52.7 MB** | **比基线还低**（全矢量绘制，不缓存位图） |

**关键定性差异**：静态壁纸是**按需渲染**（桌面基本静止，2.8fps）；
动态壁纸把它变成**常驻 60fps 重绘** —— 这是数量级的行为改变，不是"多一点"。

**内存反而更低**（52.7MB）：动态壁纸是纯 Canvas 绘制，不产生全屏位图。

**GC 不是瓶颈**：60 秒只有 1 次 GC。虽然 `LiveWallpaperRenderer` 每帧都 `new Path` + `new LinearGradient`
（极光带每帧重建路径和渐变；水面/星空的渐变也没缓存，只有夜空缓存了），
但这些都是小对象 —— app 堆才 2MB/4MB，**CPU 全花在光栅化上，不是花在分配上**。

### 4.4 S4 视频壁纸 —— 这台镜像测不出真实成本

app 进程只是喂数据，自己不干活；但**解码不在 app 进程里**，把相关系统进程一起量：

| 进程 | CPU% |
|---|---|
| `com.ecarx.cardesk`（app） | 0.88 |
| `mediaserver` | **0.00** |
| `hardware.google.media.c2@1.0-service`（真正解码的） | **0.00** |
| `media.extractor` | 0.00 |
| `surfaceflinger` | 1.48 |
| 客机整机 busy | 11.00% |

解码服务 CPU 是 **0.00%** —— 因为**这台 AVD 的镜像一帧都解不出来**
（`dumpsys media.player`：`state(5)` / `c2.android.avc.decoder` / `numFramesTotal(0)`，
系统自带 Gallery3D 播放同一文件同样全黑）。
解码器接了输入但出不来帧 → 基本在空转等待。

⇒ **这里测到的 0.87% 不是真实成本**。实车上要真解码 + 真合成 + 真上传纹理，开销会明显更高。
**视频壁纸的真实性能必须在实车复测。**

## 五、顺带挖出来的两个问题（代码层面确认）

### 5.1 轮播心跳的生命周期有缺陷

`ui/LauncherView.kt`：

| 位置 | 问题 |
| --- | --- |
| `:295` | `carouselTicker.run()` 里每次 **new 一个 Handler**（`android.os.Handler(Looper.getMainLooper())`），而不是用类里的 `handler` 字段（`:535`） |
| `:4972` | `onDetachedFromWindow()` 只做 `handler.removeCallbacksAndMessages(null)` → **清不掉轮播心跳**（它在别的 Handler 上）→ 视图 detach 后心跳还在跑 |
| `:1089` | `build()` 里 `postDelayed(carouselTicker, 1000)` **前面没有 `removeCallbacks`** → 每次重建多挂一条链 |
| `:2132` / `:4115` | 换肤（`applyTheme`）和改底栏形态（`onSettingsApplied`）都会 `build()` → **每重建一次，1 秒心跳就多跑一份** |

⇒ 长期使用的车机上，切换几次日夜主题之后，心跳的 1 秒检查就跑 N 份。
单次很轻，但**是随重建次数线性增长的常驻开销**。

**修法**（3 行）：`carouselTicker` 改用类里的 `handler`；
post 前先 `handler.removeCallbacks(carouselTicker)`；
`onDetachedFromWindow()` 里显式 `handler.removeCallbacks(carouselTicker)`。

### 5.2 动态壁纸每帧重建 Path / Shader

`ui/widget/LiveWallpaperRenderer.kt`：极光带每帧 `ribbon()` 重建 Path + 新建 `LinearGradient`；
水面渐变、星空银河渐变也是每帧新建（**只有夜空渐变做了缓存**）。
这就是那 20ms 帧耗时的主要来源。按 `(种类, 尺寸)` 缓存 shader、把 Path 的采样点预计算，
可以把这部分开销压下来。

## 六、给决策的三句话

1. **静态壁纸轮播**：CPU 随便开；但要知道**内存 +32MB**，而且切换瞬间有一次 ~25ms 的掉帧（间隔越短越频繁）。
2. **程序化动态壁纸**：**别常开**。它让桌面从按需渲染变成常驻 60fps，在这台 arm64 模拟器上 CPU ×6.6、帧都超时。
   真车算力强得多，但建议**做降帧**（比如 30fps）或只在桌面无交互时跑。
3. **视频壁纸**：性能结论**暂不可信**，得实车复测（这台镜像连一帧都解不出来）。
