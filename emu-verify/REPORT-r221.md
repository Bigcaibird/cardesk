## 一、先纠正一处归因

验收报告把 P1-2 判为「历史遗留，非第220轮引入」，依据是
「旧包 4295 写出的 `cardesk-20261119-0.txt` 也已 781KB」。

**该依据不成立。** 设备上两个日志文件的首行时间戳：

| 文件 | 首行时间戳 | 是谁写的 |
|---|---|---|
| `cardesk-20261119-0.txt` | `11-19 14:53:10` | **4296**（本轮之前那次安装 4296 的时刻） |
| `cardesk-20261119-1.txt` | `11-19 15:14:30` | **4296**（最后一次重装） |

⇒ 两个文件**都是第220轮的新代码写的**。

另一侧的证据：**第220轮之前**同一台 AVD 上，旧包写出的文件是

```
524,296 / 524,427 / 524,380 / 524,460 B      ← 512KB + 一行
```

⇒ **旧写法按 512KB 正常轮换。**

**根因**：第220轮把落盘改成「常驻句柄」后，轮换检查只剩 `openTarget()` 里那一处，
而 `openTarget()` 只在 `stream == null` 时才被调用
⇒ 句柄一旦打开，文件就能一直长（实测 3.3MB），
到 4MB 总量上限时 `trim()` 会把正在写的文件也删掉 ⇒ 一次性丢光。

⇒ **P1-2 是第220轮引入的回归**，不是历史遗留。

## 二、改了什么

| # | 改法 | 落点 |
|---|---|---|
| 1 | **写之前判轮换上限**：`writtenBytes >= MAX_FILE_BYTES` ⇒ 关句柄 + 换新文件 | `core/log/FileLogSink.kt` |
| 2 | **「取不到剩余空间」≠「空间不足」**：`availableBytes <= 0` 按「够」处理 | `core/log/FileLogSink.kt` |
| 3 | **诊断包必须含当前会话**：装不下时取**尾部**，不再 `continue` 跳过整个文件 | `core/log/Diagnostics.kt` |
| 4 | **截断文案纠正方向**：「最老的 N 个文件未包含」+「当前日志过大，已只保留最后 N MB」 | `core/log/Diagnostics.kt` |
| 5 | **日志预览不再打 NOTE_MARK**（数据不是文案） | `ui/SettingsOverlay.kt` |
| 6 | **4 条回归测试 + 变异检查** | `app/src/test/…/core/log/FileLogSinkRotationTest.kt` |

### 2.1 尾部取样的实现

`Diagnostics.copyTail()`：从 `file.length() - maxBytes` 处往后读，
**先丢掉被切断的那半行**（对齐行边界），再把剩下的写进 zip。
⇒ 包里的第一行一定是完整行，grep 时不别扭。

### 2.2 第 5 条是被第 2 条「带出来的」

以前 `hasFreeSpace()` 在取不到空间时返回「不足」⇒ **Robolectric 里根本不写文件**
⇒ 设置页的日志预览永远是占位符 `(暂无日志)`（白名单里正好有这一条）。

修好之后它真的写文件 ⇒ 预览变成 40 行**日志原文**
⇒ 被 [SettingsCopyTest] 当成「不在白名单的说明文字」报出来。

这是**标记用错了**（日志原文是数据，不是说明文案），所以改标记而不是改白名单 ——
否则日志里只要出现 `FORBIDDEN` 里的词（「开机后进入本桌面」等），
「啰嗦文案不许再出现」这条用例会**误报**。

### 3.5 本轮验证时**自己**挖出来的第三个问题：截断文案的单位

把日志跑到 **2.1MB** 再导出诊断包，摘要里赫然写着：

```text
⚠ 当前日志文件过大，已只保留**最后 0 MB**（最近的内容都在里面）
```

**「0 MB」是错的。** 实际保留了 **486,524 字节（475 KB）** ——
因为包体上限 2MB 会被前面几个整文件先占掉大半，
留给最老那个文件的尾部只剩几百 KB；
而文案按 `bytes / 1024 / 1024` 取整，475KB 就被算成了「0 MB」。

看的人只会以为「什么都没保留」——**比不写还糟**。

修法：加 `humanBytes()`，≥1MB 用 MB、≥1KB 用 KB、否则用 B。

```kotlin
internal fun humanBytes(bytes: Long): String = when {
    bytes >= 1024L * 1024L -> "${bytes / (1024L * 1024L)} MB"
    bytes >= 1024L -> "${bytes / 1024L} KB"
    else -> "$bytes B"
}
```

补了一条单测锁住它（`尾部不足 1MB 时截断文案不能写 0 MB`）。

**这条是本轮验证自己发现的，不是验收报告提的** ——
所以交付版本从 4297 升到 **4298**（只多这一处文案 + 一条单测，逻辑零改动）。

> 顺带记一笔：这条单测第一次跑**是失败的** ——
> 我把 486,524 B 写成了「486 KB」（486 是字节数不是 KB）。
> 486524 ÷ 1024 = **475** KB。测试当场把这个算术错误抓了出来。

## 四、验收留下的那个 ⚠：同口径翻页 A/B

验收要求「用同一脚本、同一帧率、同一间隔对 4295/4296 做 A/B」。

### 4.1 先修测量环境

第一次 A/B 的噪声极大（同一包能跑出 0% ~ 18%）。查出四个噪声源：

| 噪声源 | 实测 | 处理 |
|---|---:|---|
| 领克 5570 模拟器 | **188% 宿主 CPU** | 停掉（用户已要求不再用它测试） |
| `basetest28`（5562） | 内部**全空闲**却占 **181% 宿主 CPU** | 停掉（启动参数已记在 §6，可随时重启） |
| AVD 上跑着高德地图（259M）+ uni-launcher | — | 重启 AVD 后 `force-stop` |
| `surfaceflinger` 2.1GB / `media.codec` 空转 124% CPU | — | 重启 AVD 清掉 |

### 4.2 清理后的交替 A/B（三轮）

同一台设备、同一脚本 `/data/local/tmp/swipe12.sh`（12 次翻页，0.35s 间隔）、**交替**跑以摊平噪声：

| 轮次 | 4295 旧包 | 4297 新包 |
|---|---|---|
| #1 | 94 帧 / **6 janky (6.38%)** / missed 0 / Slow UI 3 | 90 帧 / **0 janky (0%)** / missed 0 / Slow UI 1 |
| #2 | 92 帧 / **0 janky (0%)** / missed 0 / Slow UI 0 | 93 帧 / **1 janky (1.08%)** / missed 0 / Slow UI 1 |
| #3 | 93 帧 / **9 janky (9.68%)** / missed 0 / Slow UI 4 | 92 帧 / **1 janky (1.09%)** / missed 0 / Slow UI 1 |
| **中位** | **6.38%** / Slow UI 3 | **1.08%** / Slow UI 1 |

**判读：**

1. **Missed Vsync 两包全程都是 0**，最长帧都 ≤32ms ⇒ **没有可感知的卡顿回归**；
2. jank 百分比在这台 AVD 上**噪声极大**（同一包 0% ~ 18%），
   **不能当验收硬指标** —— 验收报告「不能据此判回归」的判断是对的；
3. 干净环境下中位数方向**对新包有利**（6.38% → 1.08%）。

### 4.3 为什么上一版报告的 3.23% 也没意义

`93 帧 ≈ 260ms × 30fps × 12` —— 那次采样是 30fps 口径，
这次是 60fps，**帧数根本不是同一个量** ⇒ 百分比不可直接比。
这正是验收指出的问题，现在用 A/B 把结论补齐了。
