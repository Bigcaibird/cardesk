> ⇒ 视频壁纸下**不再做任何浮层增强**，浮层文字直接压在视频画面上。
> 保留本章作为**决策记录**：这条路的做法、实测数据、踩过的坑都在这里，

> 上一轮（第215轮）给桌面浮层加了「描边 + 底衬」，效果达标。
> 但本轮在 4291 发布包上做冒烟时，**发现第215轮改错了组件** ——
> 顶栏右上角的时间「10:36」在日间模式下仍然看不清。

## 一、问题：第215轮改错了组件

### 1.1 实测现象

4291 装机冒烟（日间模式 + 视频壁纸）：

```
顶栏右侧 · 时钟「10:36」   对比度 = 1.95  ❌ 看不清
```

把该区域放大后能直接看出：**深色的「10:36」裸文字直接压在深蓝色视频画面上，没有任何描边、也没有底衬**。

### 1.2 根因

第215轮给「顶栏」加描边时，改的是：

| 文件 | 内容 | 实际在屏幕上的位置 |
|---|---|---|
| `ui/widget/StatusBarView.kt` | 时间/日期/续航/车外温度 + 齿轮/电池/wifi/蓝牙图标 | **左侧**「驾驶模式 · 待命」那一块 |

而**屏幕最上方那条真正在用的顶栏**是另一个组件：

```
ui/shell/ShellStatusBar.kt   ← 右上角：时间 / 油量% / 燃油图标 / 连接图标 / 位置胶囊 / 天气胶囊
```

于是：

- `ShellStatusBar` 里的**时钟**、**油量百分比**、**燃油图标**、**连接类图标**
  全都是**裸元素**（没有胶囊底衬），视频壁纸下一律直接压在画面上；
- 位置胶囊 / 天气胶囊因为**自带胶囊底板**，所以没露馅（截图里能看见底衬）。

### 1.3 为什么夜间没暴露

夜间 UI 的文字是**浅色**（`0xFFEEF3FA`），压深色视频画面本来就可读（实测 9.83），
所以这个缺陷**只在日间模式 + 视频壁纸**下暴露 ⇒ 上一轮专门测日间时，
恰好只测了 `ScenePage` 的天气块和 `StatusBarView`，把这条漏过去了。

## 二、修法

### 2.1 改动清单

| 改动 | 文件 | 要点 |
|---|---|---|
| **描边倍率** | `core/Skin.kt` | `drawOverlayStroke()` 增加 `strokeScale` 参数（默认 1，不影响既有调用） |
| **时钟描边** | `ui/shell/ShellStatusBar.kt` | 走 `Skin.drawOverlayStroke`，倍率 `CLOCK_STROKE_SCALE = 1.6` |
| **油量%描边** | `ui/shell/ShellStatusBar.kt` | 同上（17px 裸文字） |
| **图标描边** | `ui/shell/ShellStatusBar.kt` | 燃油图标 + 5 个连接图标（蜂窝/热点/WiFi/蓝牙）：先画**对比色加粗**的同形图标，再画原本色的 |
| **描边色** | `core/Skin.kt` | 沿用第215轮：日间浅色 `0xE6FFFFFF` 压深字、夜间深色 `0xB3000000` 压浅字 |

### 2.2 为什么图标也要「两遍画」

`android.graphics.Paint` **没有 `strokeColor`**（描边和填充共用 `color`），
`Paint.setShadowLayer` 在**硬件加速** Canvas 上直接被忽略
⇒ 描边只能靠「先画对比色空心加粗、再画原色实心」两遍实现。

图标是**纯线条**（`iconPaint` 是 `Style.STROKE`），
描边层 = 同一条路径 + **加粗** + 换色：

- 线条类（蓝牙/热点弧/WiFi 弧/燃油）：线宽 `+ ICON_OUTLINE_PAD (2.6)`（26×26 基准坐标系里）；
- 实心类（信号条/WiFi 点/热点圆心）：形状本身**外扩** `ICON_OUTLINE_PAD_FILL (1.4)`。

### 2.3 为什么时钟要单独的描边倍率

`Skin.overlayStrokeWidth(textSize)` = `max(1.5, textSize × 0.07)`：

| 字号 | 默认描边 | 说明 |
|---|---|---|
| 96px（温度大字） | 6.7px | 有底衬，够用 |
| 32px（**顶栏时钟**） | **2.24px** | 裸文字，在 1920×1080 上几乎看不出 |
| 17px（油量%） | 1.5px | 同上 |

⇒ 给时钟单独加 `CLOCK_STROKE_SCALE = 1.6`（≈3.4px），其余保持默认。

### 2.4 对静态壁纸零影响

`Skin.overlayOnVideo` 只在视频壁纸播放时为 `true`，静态壁纸下描边层**一遍都不画**
（单测 `静态壁纸下一遍描边都不画` 断言计数为 0）。

## 五、踩到的坑

### 5.1 「测试全局状态泄漏」引发的**随机**失败

第216轮第一次跑全量 JVM 单测，出现 1 个失败：

```
com.cardesk.launcher.ui.LyricsPreviewRenderTest > 渲染三行大字歌词
  java.lang.AssertionError: 上一句与下一句高度应一致 expected:<40> but was:<41>
```

这条断言跟本轮改动**毫无关系**（歌词预览的行带像素统计），单独跑是绿的。

二分定位：

```
歌词 + SkinOverlayLegibilityTest        → FAILED
歌词 + ShellStatusBarOverlayTest        → BUILD SUCCESSFUL
```

根因：**`Skin.overlayOnVideo` 是全局可变开关**，而第215轮的
`SkinOverlayLegibilityTest` 里有几个用例把它设成 `true` 之后**没有还原**。
泄漏出去之后，`ScenePage.drawCenterLyric` 的 `haloWidth` 跟着变大，
歌词字形轮廓外扩一圈 ⇒ 差分出来的行带高度从 40 变成 41。

而 JUnit 的**方法执行顺序是不确定的** ⇒ 谁最后跑谁说了算
⇒ 第215轮那次全量恰好绿、第216轮这次恰好红 ⇒ **这是个 flaky，不是回归**。

修法：给两个测试类都加 `@After` 强制还原全局状态，
**不靠用例内部自觉调**（顺序不定，靠自觉必然漏）。

### 5.2 变异检查里的「计数断言」不够严

第一版把 `overlayStrokePassCount++` 放在**绘制调用之前**，
结果「把绘制调用删掉」这种变异**不会**让计数变化 ⇒ 断言空跑，变异检查当场漏网。

⇒ 计数必须放在**调用之后**（更严格地说：放在**绘制函数内部**，
只有真的走到描边分支才算一次）。

### 5.3 「整条顶栏一起画」会掩盖图标描边层的错色

变异③（把图标描边层错用正文色）第一版**没被捕获** ——
因为时钟/油量的描边层（走 `Skin.drawOverlayStroke`）已经把画面点亮了，
像素断言照样通过。

⇒ 给 `ShellStatusBar` 加了一个只画图标段的测试观测口
`drawIconRowForTest()`，单独判定图标描边层的颜色。
